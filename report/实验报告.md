# PLC 结构化文本代码生成与验证实验报告

## 摘要

本作业构建了一个面向 IEC 61131-3 Structured Text 的数据集和轻量 Agent harness，并设计了“既有 Agent × 两个基础模型”和“自研 harness × 两个基础模型”四组对照。数据集包含给定题库的 20 道公开题和 10 道原创合成题，共 30 题；每题均有接口、假设、scan-level LTL 规约和测试场景。

统一离线复测覆盖全部 120 份归档最终源码。52 份通过、3 份被 CODESYS 拒绝、65 份因缺少结束标记或注释未闭合被完整性检查拒绝。120 份源码哈希均一致。历史 90/120 和 30/30 属于旧项目构建记录，不能用于当前编译判定。 Pi 关闭工具并只生成一次，自研策略允许两轮编译反馈修复。两组比较反映这两种具体策略的表现。题库 v1.2 的规约未用于原始源码生成。 历史 Control Win 执行 88/224 项，82 PASS、6 FAIL。P02 自动测试 20/20，CBMC 有界检查 918 项通过。

IDE 模拟器另执行了 51 份符合接口的归档源码，共 199 个场景组合，195 PASS、4 FAIL，覆盖 19 道题和 72/112 个场景 ID。48 份源码整套通过。P05、P14 的三份人工修订另通过 9/9 个场景。本轮无模型调用。

## 3. 数据集与形式规约

### 3.1 来源与题目覆盖

公开部分逐题取自作业提供的题库 JSON，原始 PDF 和 JSON ZIP 随包保存在 `dataset/sources/`，抽取件保存在 `dataset/question_bank_original.json`。公开题保留源题名称与接口字段；为使控制行为可重复，题目另附边界条件和 scan timing 等假设。每题的 `source` 与 `adaptation_notes` 字段指明原题来源及处理方式。

10 道自建题是原创合成，不把原始题面拼接成新题。题目覆盖泵组轮换、输送带堵塞回退、液位滞环、配方混合、风机分级、压缩机轮换、门禁停机、剔除脉冲、双罐转移和加热器诊断。设计时为每题定义 I/O、状态边界、定时条件、优先级或复位逻辑，并人工检查安全态、阈值边界和 LTL/需求的一致性。

| 来源 | Easy | Medium | Hard | 合计 |
|---|---:|---:|---:|---:|
| 给定公开题库 | 6 | 8 | 6 | 20 |
| 原创合成题 | 4 | 4 | 2 | 10 |
| 合计 | 10 | 12 | 8 | 30 |

难度按控制状态和逻辑结构定义，而不是按代码行数定义：Easy 侧重单状态、联锁、滞环或定时；Medium 涉及多步顺序、模式切换、故障恢复或数值边界；Hard 涉及队列、动态选择、阶段自动机、双设备轮换或多状态安全转移。30 题共含 279 项带方向和类型的接口字段、207 条 LTL 规约和 112 个测试场景；每题至少 3 条规约和 3 个测试场景。接口审计后，10 道自建题均补齐机器可读 I/O；自建题规范源文件为 `dataset/synthetic_tasks.json`。

### 3.2 Scan-level LTL 约定

规约将 PLC 每一扫描周期作为一个离散时刻：`G p` 表示每一扫描周期均满足 `p`，`X p` 表示下一扫描周期满足 `p`，`F p` 表示未来某一扫描周期满足 `p`。布尔连接符和比较式按通常逻辑解释。TON 完成、阶段状态、前一扫描值等用有名称的原子命题表示。

此表示强调周期边界上的因果和安全属性。`timerDone` 等原子需要由目标运行时模型解释；`AtMostNOf(...)`、`validIPv4` 等命名宏需在 verifier adapter 中按目标工具语法展开。由于本机没有 PLCVerif，当前 LTL 尚未交给形式化工具解析或验证；规约文本可审查不等于模型检查通过。

## 4. 自研 Agent 设计

Agent 使用任务 JSON 作为单一事实源，把自然语言要求、接口、假设、LTL 和测试场景拼成一个模型输入。它保存完整单题上下文，不在任务间共享状态；这样可降低跨题信息污染，但目前尚未实现长上下文压缩。模型适配器通过 OpenAI-compatible Chat Completions 调用 DMXAPI；生成结果提取为单个 ST 程序并保存。

```text
题库 JSON
   ↓
任务选择与需求上下文组装
   ↓
模型适配器 ──→ Pi 单轮基线（无工具）
   │
   └──→ 自研 Agent harness
             ↓
        ST 代码提取与保存
             ↓
        轻量静态预检
             ↓
        编译器 adapter ──→ CODESYS 3.5.22.40
             ↓
        编译失败时的有限修复回路
             ↓
        输出、token、费用及诊断 CSV
```

自研 harness 的任务输入包含题面、接口和已记录假设，避免模型自行发明 I/O。CODESYS 编译器适配器以新建的 Control Win x64 项目构建生成的 PROGRAM、FUNCTION_BLOCK 或 FUNCTION，并保存完整诊断。harness 按 `repair_limit` 限制重试；成功、编译器不可用、超时或达到次数上限后停止。默认上限为 2 次修复。若目标编译器不可用，harness 只返回生成状态和轻量静态预检结果，不把静态预检失败伪装成编译结果。

静态预检只检查程序单元声明、结束标记、`VAR/END_VAR` 和少量控制结构结束标记，不进行 IEC 语法解析、类型检查或目标平台编译。真实编译由 `src/compiler.py` 中的适配器负责；真实测试还需要 PLC 仿真器或可执行的 ST runtime，本次未提供假运行结果。

Pi 基线使用相同任务 prompt 和系统规则，关闭文件、shell 等工具，并固定到相同模型接口。它与自研 harness 的资源差别是自研 harness 可以取得编译器反馈并修复，基线不修复。因此完整实验应同时比较首轮输出，并单独报告修复后结果；当前 pilot 将修复轮数置为 0。

## 5. 实验设计与指标

四个实验条件为 Pi + GPT、Pi + DeepSeek、自研 harness + GPT、自研 harness + DeepSeek。完整设计为每条件覆盖 30 道题，共 120 个条件-题目单元；固定温度为 0，模型 ID、题目、假设、LTL 和系统 prompt 对齐。任务运行顺序由固定随机种子打乱。正式条件允许自研 harness 最多修复两次。

主要指标定义如下：

1. 首轮编译通过率：首次 CODESYS 编译成功数除以该实验条件的任务总数；没有生成非空 ST 的任务按端到端失败计入。另报告已提交编译代码中的条件通过率，以区分生成失败和编译失败。
2. 修复后编译通过率：最终 CODESYS 编译成功数除以该实验条件的任务总数；没有生成非空 ST 的任务按端到端失败计入。另报告已提交编译代码中的条件通过率，并报告修复次数。
3. 测试通过率：通过测试场景数除以实际执行场景数；同时报告全场景通过的任务比例。
4. 形式验证：逐题记录 PASS、FAIL、TIMEOUT 和 NOT_RUN，不将未运行项算作通过。
5. 资源指标：模型 token、供应商实际费用、端到端耗时和修复次数。

## 7. 有效性边界与后续工作

Pi 关闭工具并只生成一次，自研策略允许两轮编译反馈修复。两组比较反映这两种具体策略的表现。题库 v1.2 的规约未用于原始源码生成。 统一离线复测覆盖全部 120 份归档最终源码。52 份通过、3 份被 CODESYS 拒绝、65 份因缺少结束标记或注释未闭合被完整性检查拒绝。120 份源码哈希均一致。历史 90/120 和 30/30 属于旧项目构建记录，不能用于当前编译判定。 历史 runtime 和 P02 CBMC 结果仍适用于各自的原始测试范围。新版功能向量已在 CODESYS IDE 模拟器中覆盖 51 份源码和 199 个场景组合。全题 LTL 自动验证仍未执行。

后续工作可以按以下顺序推进：
